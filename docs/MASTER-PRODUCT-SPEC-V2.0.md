## 产品总体规范、体验设计与技术研发主文档

**Master Product Specification / 产品主规范 V2.0**

更新日期：2026 年 11 月 2 日

文档性质：产品方向、品牌、功能、交互、视觉、工程、研究和验收的统一依据。

适用对象：ChatGPT、Work、Codex、产品设计师、视觉设计师、交互设计师、Agent 工程师、前端开发者及独立评审者。

# 01｜项目定义与长期目标

## 1.1 产品名称

**ORIMERI**，当前工作名称。

尚未完成正式商标、近似品牌、域名及社交账号的全面核验，不视为最终清查通过的品牌。

此前探索过 Elsewhere、Tastance、Avondo 等名称，其中 Avondo 已因已有品牌使用等问题被否决，不应重新启用。

## 1.2 已确定的品牌标语

**Same taste. Different moments.**

**品味如常，心境不同。**

这是已经确定的中英文表达，后续不得擅自改写。

标语所表达的产品假设是：一个人的文化兴趣可能保持相对稳定，但现实生活中的目标、情境和约束不断发生变化。

产品需要让这两者共同参与选择，而不是简单依据用户过往喜好重复推荐。

## 1.3 一句话产品定义

ORIMERI 是一款以文化品味和当下意图为基础、由 AI Agent 协助探索、判断和修订现实体验的交互式智能产品。

用户可以通过自然语言与可操作的文化对象表达自己。Agent 使用可信的数据来源调查可能性，形成有依据的提议，并允许用户直接质疑、修改和撤销判断。

## 1.4 产品不是什么

ORIMERI 不是：

- 普通旅游推荐网站。
- 将 ChatGPT 对话框包装成地点搜索的工具。
- 只有音乐、电影、品牌标签的推荐引擎。
- 将文化内容排成网格的收藏管理系统。
- 旅行杂志、文化媒体首页或生活方式电商。
- 使用虚构关系图和百分比制造智能感的 AI 仪表盘。
- 为每个用户输入重新生成任意界面的通用 UI 引擎。

**产品的核心是人与 Agent 共同作出、理解和修改一个具体选择的过程。**

## 1.5 双重目标

### 近期目标：比赛成果与可靠性

面向 2026 Qloo Agentic Hackathon，已完成正式投稿。

现阶段重点是：

- 确保评审期间 Demo 可持续访问。
- 核实真实 Qloo 与 Agent 的功能。
- 消除严重功能缺陷、数据误导和安全风险。
- 准备能够独立验证的技术及产品证据。
- 如入围，准备现场演示与问答。

比赛四项等权评价维度为：

1. 技术实现。
2. 产品设计。
3. 潜在现实影响。
4. 创意质量。

获奖是竞争目标，不是已经实现或可以保证的结果。

### 长期目标：独立产品与可复用能力

不把 ORIMERI 永久限制在东京、旅行或地点发现。

长期探索的是：

**文化品味、现实情境与人机协作之间的新型交互关系。**

首个用例选择文化地点，主要因为它方便验证 Qloo 的跨领域关联和现实约束。

未来可以研究其他文化发现、生活选择、人与 Agent 协作和多 Agent 决策场景，但新增方向需要独立验证，不自动进入产品路线图。

长期应积累：

- 自有品牌。
- 可编辑产品源码。
- Moment Space 交互模型与组件。
- 用户研究与行为证据。
- Agent 数据与任务契约。
- 独立视觉系统。
- 可迁移、可维护的技术能力。

# 02｜真正需要解决的用户问题

## 2.1 初始目标人群

首批研究对象为具有跨领域文化兴趣，希望将音乐、电影、书籍、设计和品牌等个人喜好转化为现实体验的人。

例如，一个人喜欢 Brian Eno、王家卫、Dieter Rams 和 Aesop，但这并不意味着他在所有时间都喜欢同一类场所。

他可能：

- 今晚想找安静读书的地方。
- 周末想认识有共同文化兴趣的人。
- 旅行时希望探索当地独立文化空间。
- 不想去酒吧。
- 需要一定距离内的地点。
- 临时改变计划，但不想从头解释自己的全部偏好。

这些是优先验证的使用情境，不应直接写成已有大规模用户需求证据。

## 2.2 核心用户任务

用户想完成的是：

> 找到一个与我的文化兴趣存在有据关联，同时符合我此刻真实需求的选择。当 Agent 判断不合适时，我能指出具体原因，而不需要重新开始整个过程。

关键不是“推荐了多少地点”，而是：

- 有没有理解当前目标。
- 有没有保留需要保留的个人偏好。
- 有没有遵守现实硬约束。
- 是否能解释依据。
- 能否承认未知。
- 用户能否直接纠正。
- 修改后是否保持一致。

## 2.3 最重要的待验证假设

H1：跨领域文化兴趣有助于发现传统关键词搜索容易遗漏的候选。

H2：长期偏好与当前情境分别建模，能改善现实选择的适用性。

H3：直接操作某条提议依据，比反复通过普通聊天重新描述需求更容易完成局部纠正。

H4：可检查、可修订的提议会提升用户对 Agent 判断边界的理解。

以上均为产品假设，而不是已经验证的结论。

# 03｜产品核心：Moment Space

## 3.1 定义

**Moment Space（此刻空间）是 ORIMERI 的核心交互框架。**

它是一种人与 Agent 围绕共享任务持续协作的自适应界面。

它不是单独的页面，不是固定形状的图形，也不是普通的聊天记录。

它的设计目标是让人和 Agent 操作同一个持续存在的选择，而不是交替产生一串不相关的信息。

## 3.2 五类核心对象

### Taste｜长期品味

用户已经确认的文化兴趣。

包括音乐人、电影、书籍、设计师、品牌等。

每个对象至少应有：

- 实体名称。
- 实体类别。
- 真实 Qloo 实体 ID 或对应来源标识。
- 用户是否确认。
- 可用的图片与来源。
- 添加、移除和纠正状态。

用户表达“今晚不想去酒吧”，不能据此自动删除其长期喜欢的音乐或文化兴趣。

### Moment｜当前意图

描述用户在当前情境中想实现什么。

可包含：

- 自由语言表达。
- 目标城市及地点。
- 搜索半径。
- 当前活动和目的。
- 明确排除条件。
- 时间与其他现实约束。
- 可协商的偏好或取舍。

不能把人类意图限制成三个预设心情。

### Proposal｜Agent 提议

Agent 根据文化数据和当前要求形成的具体选择。

它是共享工作空间中的主要操作对象。

至少包含：

- 当前候选身份。
- 提议原因。
- 使用了哪些已确认条件。
- 对应证据。
- 未确认事项。
- 可执行的质疑或修改入口。
- 当前状态与历史版本。

### Evidence｜依据

每条判断应具有可追溯的数据基础。

必须区分：

1. Qloo 提供的文化关联。
2. 可靠外部来源提供的现实信息。
3. Agent 基于已有资料形成的解释。
4. 尚未核实或无法确认的信息。

Evidence 不只是说明文字，应当能够被用户直接点选和质疑。

### Revision｜修订

记录用户与 Agent 对当前选择的修改。

至少包含：

- 原提议。
- 用户质疑的具体对象。
- 新增或改变的条件。
- 保留的长期偏好。
- 重新调查结果。
- 新提议。
- 修改理由。
- 可恢复的状态快照。

撤销必须恢复一致的状态，不能仅恢复表面上的推荐卡片。

## 3.3 四种核心交互阶段

### Express｜自由表达

用户可以自然表达完整需求，也可以操作文化对象与条件。

系统不强制复杂问卷。

### Clarify｜必要澄清

只有当歧义会实质改变查询或判断时，Agent 才提出一个有意义的问题。

例如 Aesop 指护肤品牌还是其他同名实体。

不应对每个输入都强迫用户确认。

### Propose｜提出建议

真实候选进入共享空间。

用户能看到它与文化参照、地点、现实约束以及未知因素的关系。

### Revise｜局部修订

用户可以直接点击提议的一部分，提出问题或修改要求。

Agent 在保留其他有效条件的前提下重新调查、调整或说明无法核实。

## 3.4 稳定与变化原则

稳定的对象：

- 已确认文化参照。
- 任务身份。
- 有据事实。
- 未发生变化的约束。
- 用户已经完成的选择。

可以变化的对象：

- 当前目标。
- 正在调查的候选。
- Agent 的关注焦点。
- 有变化的依据。
- 当前提议。
- 局部修订工具。

界面的视觉变化应对应这些实际变化。

不得让整个画面每次随机重新排列，损害用户的空间记忆。

# 04｜核心用户旅程

以下是 ORIMERI 的第一条标准验收情境。

## 状态 A｜建立个人文化世界

用户选择：

- Brian Eno
- In the Mood for Love
- The Little Prince
- Dieter Rams
- Aesop

点击文化对象可以查看、确认、取消或纠正实体。

图片是可探索的内容，不只是装饰。

文化兴趣可以跨领域存在，不要求用户预先选择固定文化身份。

## 状态 B｜表达当前需求

用户输入：

“想在东京涩谷附近 5km 找一家能安静读一小时书、有一点生活气息、今晚不是酒吧的地方。”

用户可以随时修改当前意图和现实限制。

示例文案必须与真实输入状态清楚区分。

点击“使用此示例”后，示例要真正进入输入值，而非仅作为 placeholder。

## 状态 C｜Agent 调查

Agent 进行必要的实体解析、Qloo 查询、地理约束处理及结果检查。

用户看到的是实际调查状态，而不是伪造的思考过程。

允许展示真实的已完成步骤，但不显示没有依据的进度百分比。

错误、无结果和限流均应清楚告知且允许恢复。

## 状态 D｜形成提议

Agent 选择一个具有实际数据来源的候选作为主要提议。

其他候选可以辅助比较。

主要提议展示：

- 真实地点名称。
- 可靠视觉资料或明确的无图回退。
- 位置及范围。
- 文化依据。
- 当前条件的匹配程度及其依据。
- 未核实信息。
- 可直接操作的判断。

文化关联不等于场所适合阅读，也不等于现场真实安静。

## 状态 E｜用户质疑

用户点击：

“这里真的适合安静阅读吗？”

在被点击的判断附近展开上下文交互。

用户继续提出：

“我更想去书店，不想去餐厅。”

Agent 应识别这是当前需求的修订，不是用户长期文化品味的重置。

## 状态 F｜修订、对比和撤销

Agent 根据真实数据重新调查。

如果存在更合适的候选，更新提议。

如果证据不足，明确说明不能确认。

界面应清楚展示：

- 原建议与新建议。
- 哪些条件改变。
- 哪些偏好保持不变。
- 哪些证据新增或失效。
- 为什么发生变化。

允许用户撤销、继续提问、保存或开始新的探索。

# 05｜UI/UX 总体设计规范

## 5.1 整体设计目标

ORIMERI 必须是一款有独立视觉语言、具有文化敏感度和真实交互品质的数字产品。

设计要有作者性、辨识度和细节，但不能牺牲易用性。

不能依靠“高级感”“未来感”“实验感”等抽象形容词代替具体设计工作。

需要综合考虑：

- 内容本身。
- 字体与字形。
- 信息层级。
- 构图比例。
- 图片与材质。
- 空间关系。
- 视觉节奏。
- 动态转换。
- 交互反馈。
- 响应式与无障碍。

## 5.2 已否决的视觉方向

过去多轮设计已经明确否决：

- 米白色文化旅行杂志。
- 暗光咖啡馆摄影充满全屏的生活方式首页。
- 黑色与荧光科技色的通用 AI 软件。
- 蓝紫渐变和发光 AI 球。
- 随机文化星座与复杂节点网络。
- 密集科学仪器、雷达和虚构百分比。
- 大标题、彩色矩形和普通卡片堆叠的 PPT 式页面。
- 只有表单、图片卡片和地点列表的常规搜索网站。
- 没有实质操作机制的视觉动画。
- 缺乏辨识度的三条交叠圆环、普通方块字标或几何符号。

这些方案中的局部排版、图片处理或交互方法可以研究，但整体视觉不能照搬。

## 5.3 色彩原则

用户不满意过去的灰紫、米白砖红、整屏深黑，以及过度突兀的蓝色或荧光色。

目前**没有经过最终验收的正式品牌色板**。

新的设计必须基于真实产品场景建立色彩系统，而不是直接换几个色号。

建议设计具有：

- 清晰、克制的基础界面。
- 有辨识度但不过度使用的品牌色。
- 真实文化内容本身的丰富色彩。
- 明确的交互和状态反馈。
- 足够的文字对比度。
- 浅色、深色和系统主题的协调版本。

用户总体偏好冷白、清晰、有编辑设计判断的视觉语言，但不应将这一偏好理解为整个产品必须只有冷色。

## 5.4 字体和信息层级

桌面主要标题通常可在 30–40px 范围内根据场景设计。

正文一般以 16–18px 为基础，辅助文字保持清晰可读。

不要在大尺寸桌面画面中使用密集的 10–12px 文案承担主要信息。

合理控制：

- 字体家族。
- 字重。
- 行距。
- 中英文及日文字形协调。
- 对齐方式。
- 字距。
- 标题换行。
- 文字与视觉内容的比例。

不应自动使用巨大衬线标题制造杂志效果。

## 5.5 布局原则

避免固定的三栏信息后台和大量重复卡片。

不要让用户输入区域永久占据主画面。

应根据状态改变视觉焦点：

- 搜索前：个人文化参照与当前需求。
- 调查中：可理解的任务状态。
- 搜索后：具体提议。
- 质疑时：被质疑的依据。
- 修订后：变化与比较。

稳定对象尽量维持位置，避免整个页面突兀重排。

桌面、手机和平板应根据具体任务重新安排信息，而不是机械压缩。

## 5.6 文化内容可视化

音乐、电影、书籍、设计师和品牌应具有文化身份，而不是统一变成灰色占位卡。

可使用：

- 有权使用的真实封面。
- 真实人物图片。
- 官方提供的文化资料。
- 可追溯来源的视觉内容。
- 明确不冒充原作的高质量文字回退。

没有图片时，应缩小或重构内容区域，避免显示大面积“暂无可用影像”。

文化对象应允许直接操作，不只是观看。

## 5.7 地点及证据可视化

真实地点应成为用户可理解、可选择的对象。

地图只能根据真实坐标绘制。

文化关系必须有实际 Qloo 数据支持。

Agent 的推断和现实未核实信息不能被包装成已经证明的事实。

关系可视化要有明确的阅读和操作价值，不能为展示技术而增加随机连线。

# 06｜交互动效规范

动效是 Moment Space 的重要组成部分，但不应成为装饰层。

## 6.1 必须具备的动态行为

**文化选择**

选择或取消文化对象时，显示明确的状态变化、焦点和反馈。

**调查开始**

用户需求保持可见；与调查有关的对象进入活动状态。

**提议出现**

真实结果到达后，主要提议成为视觉中心。

**证据聚焦**

点击具体依据后，关联内容得到聚焦，上下文操作出现。

**修订**

新旧提议发生有意义的连续变化，清楚传达保留、修改和替换的关系。

**撤销**

界面恢复先前状态，并保持空间一致性。

## 6.2 动效标准

优先使用项目已有动画实现。

一般微交互可从 150–350ms 范围开始试验，最终以真实体验调整。

避免：

- 无意义的持续旋转。
- 装饰性粒子。
- 假加载进度。
- 没有数据意义的漂浮节点。
- 过强视差和眩晕。
- 为了展示动画而阻断用户操作。

必须支持 `prefers-reduced-motion`。

动效结束后，实际 React 状态、界面内容和键盘焦点应保持一致。

# 07｜Logo、品牌与语言

## 7.1 Logo

当前历次 Logo 均尚未通过最终审美验收。

正式 Logo 设计要同时考虑：

- 字标的独立识别能力。
- 符号的独立识别能力。
- 字形比例与字距。
- 16、24、32、64px 等实际应用尺寸。
- 单色与反色表现。
- 中英文字体协调。
- 与产品动态语言的关系。
- 商标及近似使用风险。

Logo 不应只有一个概念解释，而要作为实际图形成立。

## 7.2 Slogan 使用

完整 Logo 与已确认标语应形成同一品牌组合。

桌面端优先将标语放在完整字标右侧，保留合理间距或分隔。

中文：

品味如常，心境不同。

英文：

Same taste. Different moments.

不在同一首屏反复出现多个不同版本的品牌宣言。

## 7.3 多语言

支持：

- English，默认。
- 简体中文。
- 日本語。

语言切换必须：

- 立即更新产品界面。
- 保留当前用户输入原文。
- 保留文化参照。
- 保留当前查询条件。
- 保留现有提议与修订记录。
- 保留用户选定的主题。
- 对 Agent 后续生成的说明使用所选语言。
- 避免错误翻译文化实体、人名、品牌和地点名称。

日语品牌表述尚需正式语言审校，不应将未经审校的版本视为固定标语。

# 08｜用户账户、个人空间与主题

## 8.1 访客体验

用户应当能够不登录就完成核心文化探索。

账户不应成为首次体验的阻碍。

## 8.2 个人空间

长期产品目标包含：

**My Taste｜我的品味**

已确认的文化参照、选择、修改和删除。

**Saved Moments｜保存的时刻**

保存当前意图、候选提议、重要依据与修订历史，支持恢复。

**Privacy & Data｜隐私与数据**

查看数据用途、导出、删除与隐私控制。

这些入口必须有实际功能，不能是没有后端能力的假按钮。

## 8.3 登录

可优先研究邮箱一次性链接登录，并保留访客模式。

是否使用特定认证服务，应基于现有工程、成本、隐私、可维护性和安全性决定。

不得为了页面完整而创建不能工作的注册流程。

## 8.4 外观自定义

目标支持：

- 浅色。
- 深色。
- 跟随系统。

用户可以手动选择并保存。

主题切换应使用统一设计令牌，而非简单反转颜色。

切换主题时，不能清空当前任务、文化参照或结果。

未来可以研究沉浸式视觉探索，但不应在尚未验证核心价值时建设复杂的个人主题编辑器。

# 09｜Agent 与技术系统

## 9.1 已采用的基础技术方向

目前已有工程采用或曾采用：

- Next.js
- React
- TypeScript
- Qloo API
- DeepSeek
- Vercel

最初使用 Qloo Harness 验证真实调用。

目前应优先复用现有源码和已有服务，不重新搭建另一套 Agent 应用。

实际版本、依赖和部署配置，以当前真实工程为准。

## 9.2 Agent 职责

Agent 应承担：

1. 理解自然语言和当前目标。
2. 判断哪些信息已经明确。
3. 在必要时澄清实体或约束。
4. 使用真实 Qloo 数据获取文化关联。
5. 检查地理、类别与其他现实限制。
6. 形成可审查的提议。
7. 解释判断及信息不足。
8. 响应局部质疑。
9. 重新调查并修改提议。
10. 保留和恢复一致的任务状态。

不能只是 LLM 根据用户输入生成地点名字。

## 9.3 Qloo 的正确作用

Qloo 用于：

- 文化实体搜索与消歧。
- 文化关联。
- 跨领域偏好信号。
- Insights 查询。
- 合适范围内的地点候选生成。
- 数据支持的解释信息。

必须保留来源身份和字段。

曾经实测发现，单纯将 Tokyo 作为地理偏好信号，可能返回其他国家地点。

因此需要使用符合官方 API 语义的地理过滤，并对实际坐标作必要复核。

直线距离不能伪称步行路线距离。

## 9.4 数据与事实边界

需要明确区分：

- Qloo 的文化关联。
- 实际地点资料。
- Agent 的解释。
- 尚未确认的信息。

Qloo Affinity 不能直接解释成“用户喜欢这个地点的概率”。

不能把咖啡馆、书店等类别标签直接解释为“适合安静阅读”。

不能虚构营业时间、噪声、价格、环境气氛或交通距离。

## 9.5 状态管理

建议在工程层面明确以下状态对象：

**Taste**

已确认实体及用户选择。

**Moment**

当前输入、地点、距离、排除条件与其他约束。

**Proposal**

候选 ID、数据来源、解释、证据、未知项及当前选择。

**Evidence**

证据 ID、来源、支持的判断、可信边界及状态。

**Revision**

前后状态、修订目标、保留条件和撤销信息。

局部修改不应意外覆盖长期偏好。

撤销时必须恢复相互匹配的对象状态，而非仅替换界面文字。

## 9.6 错误处理

至少包括：

- 空输入。
- 文化参照不足。
- 实体歧义。
- Qloo 无结果。
- 城市或半径无有效结果。
- API 超时。
- 限流。
- 外部信息不可验证。
- 图片加载失败。
- 新旧结果数据不一致。
- 多语言状态丢失。
- 撤销失败。

错误必须可见、具体、可恢复。

## 9.7 隐私与凭证

Qloo 与模型密钥只能留在服务端。

不向 Qloo 传递与任务无关的个人身份数据或敏感数据。

明确向用户说明数据发送到哪些服务。

公开仓库不得包含密钥、私密配置或用户数据。

日志、测试录屏和演示材料必须脱敏。

# 10｜六个核心界面状态

产品可以具有多个页面，但不能让每种状态变成彼此割裂的静态展示板。

首批统一设计和验收以下六种画面：

**01｜首页 / 当前意图**

文化参照、开放输入、地点约束与清晰探索入口。

**02｜Agent 调查中**

真实工具活动及可理解状态；允许失败恢复。

**03｜Agent 提议**

一个主要地点、真实视觉内容、候选、文化证据与未知信息。

**04｜局部质疑**

用户点击具体判断，在原位置提出问题。

**05｜修订、比较与撤销**

保留条件、旧新候选、变化理由及 Undo。

**06｜移动端**

在手机视口完整完成以上主要交互，而不只是压缩桌面画面。

这六个状态是产品设计与实现的参考，不应把之前生成的六屏概念图片冒充真实浏览器截图或实际数据。

# 11｜历史教训与明确禁止事项

过去的多轮失败不是仅仅因为审美不同，而是设计工具持续重复以下模式：

1. 只改变颜色，底层搜索表单没有变化。
2. 放大地点图片，却没有改变用户和 Agent 的协作方式。
3. 用大量装饰图形代替真实关系。
4. 将内部 Agent 流程写成产品标题。
5. 用假百分比表现文化理解。
6. 用多个平庸方案代替明确的设计判断。
7. 连续生成效果图，却没有进行真实浏览器测试。
8. 不读取已有工程，反复重建类似原型。
9. 将设计漂亮等同于产品价值正确。
10. 将“代码已修改”误认为用户体验已经改善。

正式优化必须避免这些问题。

不再接受仅靠换色、增加卡片、提高字体大小，就宣称完成产品重设计。

# 12｜专业审查与验证方法

## 12.1 UI/UX 审查

应从真实操作流程开始，观察：

- 首次进入是否理解。
- 用户能否自然表达。
- 是否知道文化参照如何选择。
- 哪个对象是当前视觉焦点。
- 用户是否能发现 Agent 的依据。
- 是否能直接纠正某一判断。
- 修改后是否知道发生了什么。
- 是否能撤销或恢复。
- 是否存在不必要的文字与操作负担。

## 12.2 工程检查

优先使用已有工程中的实际工具。

可按需使用：

- Playwright：浏览器端到端测试。
- axe-core：自动化无障碍检查。
- Lighthouse / Chrome DevTools：性能与浏览器诊断。
- React Best Practices：组件与渲染审查。
- Vercel Verification：浏览器到 API 的全链路追踪。
- Impeccable：适用时的设计审查与精修。
- Motion：确有需要时的交互动效。
- Figma：经过选择的可编辑设计系统。

先检查是否已经安装，再决定是否引入。

不为工具数量增加工程复杂度。

## 12.3 必须验证的关键案例

### 案例 A｜长期品味与当前意图

固定文化参照，分别使用两个不同的现实目标。

检查结果是否真正改变，哪些偏好得到保留。

### 案例 B｜文化证据与现实约束

使用东京涩谷 5km 和明确类别限制。

检查是否出现地理越界、场所类别不合适或无依据解释。

### 案例 C｜局部纠正

用户质疑一条具体证据。

检查是否能仅修改相关判断，而非重置整个任务。

### 案例 D｜撤销

完成一次修订后恢复。

检查输入、条件、文化参照、提议与解释是否一致。

### 案例 E｜证据不足

缺少实际噪声或营业信息。

检查 Agent 是否诚实呈现未知。

### 案例 F｜接口失败

模拟限流、超时、空结果和错误响应。

检查用户任务能否恢复。

## 12.4 公平对照

至少研究三类比较：

**LLM-only vs Qloo-grounded**

在相同任务下，Qloo 是否带来有证据支持的不同候选和文化联系。

**Taste-only vs Taste + Moment**

加入当前情境是否改善目标约束的处理，而非仅改变文案。

**Chat-only vs Moment Space**

使用相同的数据、模型能力和任务，比较局部修改的理解、效率和错误。

不能故意削弱对照组。

不虚构真实用户测试或统计结论。

## 12.5 用户体验研究

优先争取少量真实目标用户进行形成性可用性测试。

记录：

- 实际任务完成情况。
- 操作过程。
- 困惑的位置。
- 重复描述次数。
- 错误修改。
- 纠正成功情况。
- 用户如何理解依据和未知信息。

独立测试结果应区别于开发者内部主观评价。

# 17｜核心原则

**品味如常，心境不同。**

用户的文化世界有连续性，现实选择有变化。

Agent 应帮助人探索可能性，而不是替人作出不可质疑的决定。

数据应该让判断更可靠。

视觉应该让交互更清楚、更有感受力。

设计和技术应共同服务真实选择，而不是相互争夺注意力。

**这就是 ORIMERI 应当坚持的产品方向。**
